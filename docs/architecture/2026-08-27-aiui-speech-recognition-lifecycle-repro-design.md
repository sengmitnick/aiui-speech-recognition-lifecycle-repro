# AIUI SpeechRecognition 生命周期复现项目设计

## 项目定位

`aiui-speech-recognition-lifecycle-repro` 是一个可公开发布的独立 AIUI 最小复现项目，用于证明 Rokid 眼镜真机上 `SpeechRecognition` 在自然停顿、连续重启和页面生命周期中可出现“已启动但不再返回任何结果或终态事件”的假活问题。

项目同时是一个可持续演进的开发者教材：问题修复前用于复现、取证和与官方沟通；官方修复后保留历史证据，增加修复版本验收结果，并转化为 AIUI 连续语音交互文章和教程。

## 交付边界

- 仓库根目录用于公开文档、测试、证据和采集工具。
- 可直接导入 Rokid Craft 的完整 AIUI 源码必须全部位于 `src/` 目录。
- Craft 使用者只需选择 `src/` 文件夹，不需要了解仓库其余工具。
- 项目不包含剧本杀、宠物、LLM、TTS、摄像头、账号或云端业务逻辑。
- 应用只申请麦克风权限，不保存音频，不主动上传识别文本。

## 复现交互

应用只使用一个全屏页面，提供两个可对照的识别模式：

1. **单次识别基线**
   - 用户主动开始一次识别。
   - 原生会话返回结果、错误或结束后，应用不再自动重启。
   - 该模式用来证明单次 `SpeechRecognition` 通常能够正常工作。

2. **自动续听复现**
   - 用户主动开始一轮语音。
   - 原生会话在自然停顿处结束后，应用短暂等待并自动开启下一个原生分段。
   - 用户按固定句子和停顿节奏连续说话，直到出现不再返回文本或终态事件的会话。
   - 复现页面不使用自动中止或自动恢复来掩盖现象。

镜腿上下滑动在两个模式间移动选择，单击执行当前操作，返回键中止当前测试并释放原生识别会话。在 Craft 中使用对应的方向和确认按钮即可完成相同流程。

## 状态和可观测性

页面始终显示以下信息：

- 当前测试模式。
- 用户级测试轮次编号。
- 原生 ASR 分段编号。
- 当前状态：就绪、启动中、监听中、处理中、已结束或已失去回调。
- 最近一次识别文本。
- 距最近一次原生回调的时间。
- 最近若干条生命周期事件。

每个原生回调都同时输出一条结构化控制台日志，包含统一前缀、毫秒时间、轮次编号、分段编号、事件名和事件摘要。日志事件覆盖启动请求、`onstart`、声音开始、语音开始、中间结果、最终结果、错误、结束、中止、下一分段调度和无回调观测。

无回调观测只记录证据，不调用 `stop()`、`abort()` 或新的 `start()`，确保取证工具不改变被观察会话。

## 证据体系

仓库将证据分为两层：

1. **本地原始证据**
   - 包含完整真机 `logcat`、设备属性和复现过程中的原始信息。
   - 默认被 Git 忽略，避免公开系统账号、通知、其他应用日志或非测试语音。

2. **公开精选证据**
   - 仅保留本项目的结构化事件、必要的原生 ASR / 录音服务日志、设备和运行时版本。
   - 每组证据配套一份复现记录，明确操作步骤、实际现象、关键时序和隐私检查结果。

证据采集工具只负责记录，不自动判断问题已复现，也不自动发布原始日志。

## 公开文档

项目需要提供：

- 中文为主的 README，并提供英文项目摘要。
- 一份不依赖剧本杀业务的 AIUI 系统问题报告。
- Craft 和真机复现步骤。
- ADB 日志采集、隐私检查和公开证据制作说明。
- 官方修复后的真机验收清单。
- 从复现项目转为开发教程时的文章结构提纲。

项目状态必须对外明确标记为“待官方确认”、“已确认”、“已修复待验证”或“已验证修复”之一，不在没有运行时内部证据时宣称已知具体根因。

## 测试协议

公开复现使用固定、无个人信息的句子：

1. “王秘书说他凌晨一点半”。
2. 自然停顿 2 至 3 秒。
3. “在蓝色会议室”。
4. 再次停顿 2 至 3 秒。
5. “桌上放着一份文件”。
6. 重复上述三段流程至少 10 轮，或直到出现假活。

每次公开证据都要记录设备型号、Android 版本、系统 Build、AIUI Runtime 版本、源码提交号、测试模式、成功分段数和首个异常的时序。

## 成功标准

- `src/` 可作为独立 AIUI 项目直接导入 Craft。
- 基线模式和自动续听模式在同一真机环境中可对照执行。
- 每个原生 ASR 生命周期事件都能通过页面和结构化日志同时观察。
- 假活时取证程序只记录“长时间没有回调”，不主动修复或改变原生会话。
- 原始日志不会被默认提交到公开仓库。
- 精选证据可以证明缺失发生在原生 ASR / 运行时回调边界，而不是业务文本合并环节。
- 仓库在问题修复后不需要重构项目定位，只需增加修复版本证据和正确实现说明。
